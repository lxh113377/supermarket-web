# 05 · 可量化指标、前后对比与压测数据校对

> 三张表 + 一张归因表。每张表都给了**复算命令**与**原始读数文件**；口径写清楚，读者自己可以判。

## 1. 取数口径（先说清楚，再看数）

| 项 | 取值 |
|---|---|
| 浏览器/工具 | Lighthouse **12.6.0**（由仓内 `scripts/collect-live-perf.mjs` 的 `resolveLighthouse` 解析 —— 与线上回执同一个执行器） |
| 载体 | 本机 Edge（`resolveBrowser` 解析），`--headless=new` |
| 形态 | `form-factor=mobile` + `throttling-method=simulate`（与 `.lighthouse/` 里的历史回执同配置） |
| 采样 | **交错采样 7 轮**：每轮依次跑 baseline → edge → replica（不是「先把一条臂跑完再跑下一条」） |
| 统计量 | 每条臂报 **中位 [最小~最大]**。中位数会掩掉离群，所以把方差一起摆出来（本次确实出现过 FCP 9 s 的离群样本） |
| 冷启动 | 每次 Lighthouse 默认清空存储 ⇒ 每次都是「首次访问」口径；重复访问口径见 §3 的 304 读数 |
| 请求体 | 三条臂共用**同一份构建产物**（`supermarket-web/dist` 的副本），只有服务端实现不同 |

**为什么必须交错采样**：本机单次 Lighthouse 16~60 s，磁盘/CPU/后台进程的热状态会随分钟级漂移。
实测同一份代码在两次顺序采样里的中位数差到 10%+ —— 顺序成块采样会把「时刻漂移」洗成「实现差异」。
交错采样让每条臂承受同一时刻分布，差值才是实现差值。

复算：
```bash
cd supermarket-web/rust
node scripts/measure-local.mjs --samples 7 --arms baseline,edge,replica --json docs/perf-local.json
```
原始读数：[`docs/perf-local.json`](perf-local.json)（含每轮的 FCP/LCP/SI/TBT/字节/请求数与 min~max）。

## 4. 归因：为什么 FCP 动了、LCP 几乎没动

Lighthouse 的三条臂给出了同一个 **LCP 元素**，这条读数解释了整张表：

```text
LCP 元素（三臂一致）：header.site-header > a.brand-lockup > span.brand-wordmark > span
                     文本内容「江科一站通 / 校园日常服务站」
传输最大的资源（三臂一致）：fonts/display-serif-cjk.woff2 = 215,817 ~ 216,247 B
```

- 首屏最大元素是**头部品牌字**，它用的是 215 KB 的中文展示体；
- 该字体在 `<head>` 里被 `preload`，与 JS/CSS 抢同一条 1.6 Mbps 的带宽；
- `font-display: swap` 让文本先用后备字体画出（所以 FCP 能提前），但 **LCP 要等真字体到达**；
- 于是：**LCP 是字体绑定的**，与「样式表是否内联」「外壳是否等 JS」关系不大。

三条读数与这个解释自洽：edge 把渲染阻塞清零、CSS 请求消掉 ⇒ FCP/SI 动（FCP −7.5%）；
replica 让首屏标记不等 JS ⇒ FCP/SI 明显动（FCP −21.4%、SI −19.2%）；
而 LCP 三条臂都在 4.4~4.6 s（差 −5.4% / −3.8%），因为谁都改变不了那 215 KB 字体的到达时间。

**字节归因（baseline 中位的传输构成）**：

| 类别 | 字节 | 占比 | 本次是否改动 |
|---|---|---|---|
| 字体 | 257,396 | 47.2% | ✗（**最大的单一杠杆**） |
| JS | 108,320 | 19.9% | ~（br 后 −3.7%） |
| 图片（首屏滚动到的商品图） | ~150,000 | ~27% | ✗ |
| 文档 + CSS | 25,756 | 4.7% | ✓（−18.7% 且请求 −1） |

⇒ 只要字体与图片不动，首屏的「总字节」与 LCP 就不会有大变化。这不是本次重写的失败，
而是把「剩下的大头在哪」量出来了：**字体（215 KB 中文展示体）应当做子集化 / 去掉 preload**，
这是下一步收益最大的动作（预计 LCP 可降到 1.5 s 量级），但会改变首屏字体呈现节奏，
属于视觉决策，未在本次自行执行（详见 docs/06 §2 的边界清单）。

## 5. 与线上真值的对照方式（压测数据校对）

线上有两份 2026-10-24 的历史回执（`.lighthouse/receipt-t0240.json` + 同名 JSON）：

| 页面 | FCP | LCP | server-response-time | 总字节 | 来源 |
|---|---|---|---|---|---|
| admin（supermarket-web.pages.dev） | 1,473 ms | 1,791 ms | 195 ms | 196,155 B | `admin-t0240-s1.json` |
| customer（lxh113377.github.io） | 1,256 ms | 1,572 ms | **1,582 ms** | 189,556 B | `customer-t1903-s1.json` |

**校对纪律（这三条必须一起说，否则数字会被误读）**：

1. **同工具、同配置**：线上回执与本机对照都是 Lighthouse 12.6.0 + mobile + simulate ⇒ 可以放在同一行看；
2. **不同构建、不同时刻**：线上回执是 2026-10-24 的产物，本机对照是 2026-10-26 的产物
   （这两天里字体与 CSS 都长过），⇒ **只能各自纵向比，不能把 1,791 与 4,614 横向相减**；
3. **TTFB 是托管属性，不是代码属性**：本机三条臂都在 1~2 ms（同一个 loopback），
   而线上 195 ms vs 1,582 ms 的差别来自「Pages 边缘节点」vs「GitHub Pages 静态托管」。
   Rust 边缘对 TTFB 的可控部分是「预压缩 + 流式（不边算边发）」——对应 Lighthouse 的
   server-response-time 从 0.89 ms 降到 0.43 ms（−51.9%），其余要靠部署位置与 CDN。

**自检清单**（跑完 `measure-local.mjs` 后逐条对）：

- [ ] 文档传输字节与 `measure-http.mjs` 的 `content-length` 对得上（edge 21,822 B ≈ 20,727 B + 头部/其他）；
- [ ] CSS 列为 0 且文档变大 ⇒ 内联生效（对不上说明内联没生效或缺 `_headers`）；
- [ ] `render-blocking-resources` baseline > 0 且 edge = 0；
- [ ] 请求数 edge < baseline（−1 = 少掉的样式表）；
- [ ] 字体/JS 两列与 `dist` 里的文件体积一致（对不上说明测的不是同一份产物）；
- [ ] 每次 Lighthouse 都清空存储（否则第二次拿的是缓存命中，读数会假性变好）。

## 6. WASM 侧读数

### 6.1 产物体积与初始化

| 阶段 | raw | gzip | brotli |
|---|---|---|---|
| `cargo --profile release-wasm`（opt-level=z + LTO + panic=abort + strip） | 70,233 B | 27,047 B | 23,236 B |
| 再过 `wasm-opt -Oz` | **59,670 B** | 25,746 B | **22,243 B** |

初始化：Node 侧 `WebAssembly.instantiate` + 读盘 **1.28 ms**（浏览器侧是下载 + 编译，且它**不在首屏路径上**：
空闲预热或首次调用才加载）。对比第一版 JSON 协议实现（173 KB / 57 KB brotli）—— 二进制协议 + 无 bindgen 省掉 66%。

### 6.2 微基准（`node scripts/wasm-host-test.mjs`）

```text
| 算子 | 规模 | 迭代 | wasm(ms) | JS(ms) | 比率 |
| cart_summary（纯数字）        | 20 行         | 20000 | 42.53  | 3.77   | 11.29× 慢 |
| filter 一次性（每次重传全表）  | 65 件         | 2000  | 331.06 | 23.54  | 14.07× 慢 |
| catalog_query（常驻索引）      | 65 件         | 20000 | 92.57  | 228.86 | 2.47× 快  |
| csv_export                    | 2000 行 × 8 列 | 30    | 224.19 | 46.75  | 4.80× 慢 |
| csv_export                    | 20000 行 × 8 列| 5     | 382.30 | 91.55  | 4.18× 慢 |
```

读法（这也是 docs/01 §2.3 选型的依据）：**跨边界成本**决定了 wasm 的适用范围 ——
纯数字 20 行不值得跨一次；整表编码一次比筛选本身还贵；只有把「每按键都要重做的
toLowerCase + 拼搜文」搬到**加载时**算好（常驻索引），才有 2.47× 的净收益。
CSV 在 2k~20k 行两档都不占优（输入输出都要过 UTF-8 编码这一关），故**不接入**。

### 6.3 对账（同值性）

`node scripts/wasm-host-test.mjs` 共 **30 项**逐条对账全绿，包括：

- 目录筛选：一次性与常驻两条路径 × 8 组条件（子分类/关键字/命中口味/被后台关掉的口味/升降序）；

## 8. 回归门禁建议（把判据钉在确定性量上）

| 判据 | 阈值 | 理由 |
|---|---|---|
| `render-blocking-resources`（edge 臂） | 必须 = 0 | 内联样式的直接可观察后果 |
| CSS 传输（edge 臂） | 必须 = 0，且文档 ≈ br 体积 | 内联生效的判据 |
| 首屏请求数 | ≤ baseline − 1 | 少掉的样式表请求 |
| 文档+CSS 合计字节 | ≤ baseline | 净字节不许回退 |
| `/_health` | 200 且 `db` 三态之一 | 服务与绑定就位 |
| WASM 对账 | 30 项全绿 | 同值性红线 |
| 复刻 class 面 | 缺项 = 0 | 复刻不许漂移 |
