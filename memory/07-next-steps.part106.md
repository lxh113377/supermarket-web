## R57 登记（按优先级；前提=可复算命令）

- **R57-H1（高）**：跨日再采一批性能，让 `report:live-perf` 第一次能印 `BUDGET 可立`。
  **前提修正（本轮 01:28 实测把原话证伪了）**：判据的"日"取 `fetchTime` 的 **UTC 日期**，本地 09-30 01:28 采的那批
  写的是 `2026-09-29T17:28Z` ⇒ 仍判"同日、差 0 天"。所以这条动作的时窗是**本地 08:00 之后**，不是"睡一觉起来"。
  复算命令：`npm run collect:live-perf -- --run`（批次名自动取）→ `npm run report:live-perf` 读 BUDGET 段。
  本轮 t1727 批的增量价值：customer 第一次有了第二个完整批次（之前 d2/d3/t1041 三批整批 NO_FCP），
  同日两批中位数差 **FCP −2.4% / LCP −0.2% / speed-index −7.3% / SRT −24.3%** ⇒ 顾客端比管理端稳得多，
  立线时两页的余量不该照抄同一个百分比。
- **R57-H2（高）**：`verify:limits` 的 **C5 量纲错位**——它拿"批量件数"直接和 `d1_queries_per_invocation_free=50` 比大小
  （`num > max`），而真实关系是 `1+2n ≤ 50`。后果实测可推：`n=45`（1+2×45=91 条，早就爆预算）在 C5 眼里仍是绿。
  ⇒ 登记册必须带"件→语句"的换算式，C5 比的是换算后的量。反例要造一个 45 的变异体证明它会红。
- **R57-H3（中）**：采购/供应商域。对手方证据（本轮实测）：`opensourcepos` 有 `app/Models/Receiving.php`，
  代码面搜 `"RECEIVING"` 命中 313 处、`ospos_suppliers` 10 处；本仓 0 处。流水表已经能承接 `refType='purchase'`。
- **R57-H4（中）**：登录后看板那一维仍未测（R55-G6 挂账到现在）。前提是"先有一条无需凭据的等价重页面"。
- **R57-H5（低）**：业务域清单收成单一真相源（R55-E8 原样挂着，现在散在 schema / api-contract / README 三处，本轮又加了第四处 `pii-inventory`）。
- **R57-H6（低）**：`.editorconfig` 自证（R54-H4 → R56-H4 → 三度挂账）。真要闭环要靠格式化器当唯一写手。
- **不变项**：`D1 Daily Backup` 缺 `CF_D1_BACKUP_TOKEN` / `BACKUP_PASSPHRASE` 的既定红挂到 2026-10-12；
  模拟层⇄真实 D1 语义等价无第二通道（R53-H2 起挂账）。
