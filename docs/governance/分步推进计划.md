# 分步推进计划与考核校验标准

> 本文件把治理优化拆成四步可执行阶段，每阶段的验收判据必须是机器可判的。阶段本体在 registry.json 的 phases 段。

## 一、总览

| 阶段 | 窗口 | 交付物 | 验收判据 |
| --- | --- | --- | --- |
| P1 立册与判据 | 本轮 | 登记册、四份规范、一条判据与其并入聚合链 | [registry:ac-1] |
| P2 联动与四态消费 | 第 77–78 轮 | 联动规则的机器复算、性能线四态消费、人工读数取数模板 | [registry:ac-2] |
| P3 承载面收敛 | 第 79–80 轮 | 配额红档处置、判据链与脚本数合并降档 | [registry:ac-3] |
| P4 常态化与回归锁 | 第 81 轮起 | 全阶段校验并入聚合链、撤销条件复核 | [registry:ac-4] |

## 二、P1（本轮）

**做什么**：把两类治理从「散落在若干判据头注里的口径」变成「一份机器册 + 四份人读规范 + 一条对账判据」。

**考核校验标准**：

1. 判据在真仓上 rc=0，并且其 --selftest 输出 N/M 中 N==M（自证腿含正例、违规、边界、方向相反的两条变异腿）；
2. 登记册 facts 段十三条事实全部与当场重算相等（不等即点名到键）；
3. 人读文档对登记册核心 id 的引用双向闭合（无幽灵引用、无零引用核心 id）；
4. 判据并入 package.json 的 verify 聚合链，并同时登记进 CLI 入口登记册的对应表；
5. 判据自身不带任何写盘面（无 --write 腿），不触网，不改动 functions 与 src。

## 三、P2（第 77–78 轮）

**做什么**：把联动从「写在册里的规则」变成「能当场算出结论的判据」。

**考核校验标准**：

1. 至少一条联动规则在本地可用现有登记件复算出三段式结论；
2. 缺失读数被报未验而非记绿：把人工指标的 evidence 抽掉，判据必须翻红（这条已作为 P1 的变异腿先立住）；
3. 性能线四态（GREEN/WARN/RED/NO-LINE）接入报告位，NO-LINE **不得**读成通过。

## 四、P3（第 79–80 轮）

**做什么**：把已经顶到墙的承载面收紧 —— 配额余量 0.019% 的红档处置，以及运营规模面的合并降档。

**考核校验标准**：

1. 红档指标数量不上升；
2. 每个红档指标都有一笔可归因的处置提交（要么改代码，要么改口径并写明依据）；
3. 棘轮只准单向：地板只准升、债务上限只准降。把绿档放到实测值之上会被判据当场判红（F6 腿）。

## 五、P4（第 81 轮起）

**做什么**：常态化 —— 把 P1–P3 的校验变成常驻，并复核撤销条件。

**考核校验标准**：

1. 连续两轮聚合链全绿且红档指标无新增；
2. 四份规范里每条撤销条件都实测未触发（触发即按该条撤掉对应机制，禁仅改措辞）；
3. 登记册的 measuredAt 与远端读数件的龄都在各自允许窗内（批次 ≤7 天）。

## 六、阶段推进的三条纪律

1. **分步不等于分批漂**：每一阶段结束时聚合链必须能跑，禁把「等下一阶段一起接」当延期理由；
2. **验收判据必须先红过一次**：新增判据上线当轮必须看到它因真实缺口红过（本次实测已见：文档未落盘时 F1/F3 判红），否则它是恒真条件；
3. **改口径必须留撤销条件**：每条阈值/规则都要写「出现什么证据时该条应被改写或删除」，写在对应规范末尾。

## 七、撤销条件

- 若 P2 到期仍没有一条可复算的联动结论，则本计划缩表为 P1+P4 两步，联动分析降级为「分别报告」；
- 若 P4 连续四轮无法达成（聚合链反复红在治理面自身），说明治理面已超过本仓的维护容量，应把判据降档为报告位并只留登记册；
- 若某阶段的窗口被证明是拍的（拿不出该阶段为什么需要两轮的实测依据），该阶段应合并进相邻阶段，而不是维持形式上的分期。
