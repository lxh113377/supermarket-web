# 体量治理规范（业务体量 / 资源承载体量 / 运营规模体量）

> 本目录即 supermarket-web 仓的 git 根（HEAD f2410b3）。三类体量节点登记在 `docs/governance/registry.json`（schema chaoshi-governance-registry-v1），本文以 [registry:<id>] 引用；引用存在性与登记⇄现值一致性由 `npm run verify:governance`（`node scripts/check-governance-framework.mjs`）对账。一物一判：同一体量面只允许一条判据判决，本文是口径与取数面、不是判决面，不新立任何闸（§5）。

## 1. 目的与三类体量的边界

目的：把「仓里有多少东西」拆成三个互不混淆的量，各有唯一单位、唯一定档法、唯一责任角色——既不拿业务增长解释工程预算，也不拿工程预算掩盖业务增长。

- **业务体量**：门店运营在 D1 与线上目录里的存量，不在仓内代码里。节点[registry:bl-sku]、[registry:bl-orders-30d]、[registry:bl-peak-order-items]。**不进任何体积预算**，只当资源阈值的推导基数。
- **资源承载体量**：仓内可机器读数的物理量（配额余量、产物字节、记忆卷字节）。节点[registry:rl-d1-write-headroom]、[registry:rl-firstload-js]、[registry:rl-largest-chunk]、[registry:rl-memory-volume]。
- **运营规模体量**：治理体系自身规模（判据链长、闸脚本数、CI job 数、上限登记行数、未登记件上限、性能线数）。节点[registry:op-verify-legs]、[registry:op-gate-scripts]、[registry:op-ci-jobs]、[registry:op-limit-rows]、[registry:op-no-budget]、[registry:op-perf-lines]。方向是持平或压缩。

**不计入**：数仓与备份产物体积（无登记，§6）；D1 行读取量（本地不可测，`docs/d1-write-quota.json` 的 rows_read_measurable_local=false）；营业额等财务量；构建产物总体积（只入「首屏真下载集」与「单 chunk」两口径）。

### 2.1 source.op = manual 的确切含义

[registry:bl-sku]、[registry:bl-orders-30d]、[registry:bl-peak-order-items]、[registry:rl-firstload-js]、[registry:rl-largest-chunk]、[registry:op-perf-lines] 六项今天不能机器取数（前三在运营库，后两依赖 gitignore 的 dist/，末项联网+浏览器不进 CI）。manual 意为三件齐备：① measuredBy＝当次真跑出该数的命令；② evidence＝可复核标识（构建目录/批次/回执）；③ measuredAt＝取数日期。**禁止把人工读数冒充机器现值**：measuredAt 是取证注记不是判据输入，任何判据读它即把某机某次产物当常量（`docs/item-budgets.json` provenance.warning 已成规）；引用这类指标须带日期或注明「读数」，不得与机器现值混排。

## 3. 阈值三档定档法

- **余量法**（配额/上限型）：G 余量≥10%，W 1–10%，R <1%。[registry:rl-d1-write-headroom] 现 19/100000=**0.019% ⇒ RED**（按天计，一天打爆补不回）。
- **棘轮法**（只准改善的挂账型：[registry:op-no-budget]、[registry:op-limit-rows]、[registry:rl-memory-volume] 单卷）：G 持平/改善且地板余量≥10%；W 持平但余量<10%；R 恶化一档（地板抬到等于现值，或债务上限调高）。
- **比例法**（预算型：[registry:rl-firstload-js]、[registry:rl-largest-chunk]）：G ≤85% 预算，W 85–100%，R >100%。预算值只写在 `node scripts/check-bundle-size.mjs` 的 BUDGET，本文不复制第二份。

**铁律：冻结增长就是红线。** 把地板抬到刚好等于当前值＝零余量＝宣布此后任何增长作废，且抓不到「解禁项被静默摘回面外」。故棘轮地板必须留 ≥10% 余量（`docs/item-budgets.json` 的 budget=实测×1.10，`docs/limit-provenance.md` 同规）；抬地板前先跑枚举腿现算件数，禁手抄清单。

## 4. 动态监控与自适应调整

- **频率**：每轮（[registry:rl-d1-write-headroom]、[registry:rl-memory-volume]、[registry:op-limit-rows] 类随每次推送由 `npm run verify` 系机器现算）；每日（D1 远端读数，remote_usage_max_age_days=7，日界 00:00 UTC，超龄即无效）；每次推送（[registry:op-verify-legs]、[registry:op-gate-scripts]、[registry:op-ci-jobs]、[registry:op-no-budget]）；每 7 天（[registry:op-perf-lines]，maxBatchAgeDays=7，超龄具名报「没人喂」，不得读成稳定）。
- **消费面（谁在读这些阈值）**：阈值只写在册里不会自己失败，必须有一条命令逐格消费它。现登记两条：[registry:op-perf-consume]（`npm run report:live-perf` 逐 页面×批次 消费六条性能线，四态 GREEN/PARTIAL/RED/NO-LINE/UNVERIFIED）、[registry:op-governance-consume]（`npm run verify:governance` 逐 facts 叶子对账，三态 FAIL/PASS/UNVERIFIED）。判据 F12 核「册内声明的状态集 ⇄ 命令源码里的 @consumer-states 自声明」，缺一条即红。
- **四态**：GREEN / WARN / RED / **NO-LINE**。NO-LINE＝**没有阈值消费者不算通过**：阈值存在却无判据或流程读它，即 `docs/live-perf.json` thresholdNote 自述的失效形态，不得折算 GREEN。
- **棘轮规则**：地板只准升，债务上限只准降（noBudgetMax 与 cli-legs unguardedMax 同规）。清偿与改阈值必须同一笔——先降上限会自判红，先降欠账不改上限等于放宽尺。
- **调整流程**：提出人＝该指标责任角色；批准人＝仓主人（治理评审）；可改阈值的证据＝当次实测（带 measuredAt 或构建标识）+归因+**撤销条件**；改阈值＝改代码（BUDGET）或登记册，且与文档同笔、与棘轮方向一致。
- **升级路径**：WARN→记台账排下一轮；RED→已接闸者当场阻断（`npm run verify` 系），未接闸者（[registry:op-perf-lines]）由人处置；NO-LINE→先接消费面，未接前不计入通过面；跨 3 轮无判决→按 §7 降级出册。

## 5. 与既有判据的咬合表（一物一判）

| 体量面 | 唯一判决者 | 管什么 | 不管什么 |
|---|---|---|---|
| 记忆卷字节 | `npm run verify:volume` | 单卷 ≤4096B、壳 shell_max=40960B、声明⇄磁盘双向 | 上限出处、壳外件 |
| 数值上限出处 | `npm run verify:limits` | 每个会砍东西的上限有行、对得上、类别合法 | 体积、件数预算 |
| 首屏预算 | `npm run check:size` | firstLoadJs 95KB / firstLoadCss 12KB / largestChunk 300KB | 单件分项（归 item-budgets） |
| 线上性能线 | 性能线判据（report:live-perf 别名） | thresholds 6 条与逐 页面×批次中位数 | 不进 verify/CI，红由人处置 |
| 登记册⇄现值 | `npm run verify:governance` | [registry:<id>] 引用存在、登记⇄现值一致 | 不判上列任何一物，只做对账 |

**不得重复立判据**：[registry:rl-firstload-js]、[registry:rl-largest-chunk]、[registry:rl-memory-volume]、[registry:op-limit-rows]、[registry:op-no-budget] 在本文只被引用，判决仍在既有判据。新增指标前须先证它未被上表任一行覆盖，否则同数据同口径两个判决者＝第二把尺，本仓当缺陷。

## 6. 覆盖缺口

1. **D1 行读取量**本地不可测（rows_read_measurable_local=false），只有 7 天失效的远端读数 ⇒ 不得把「本地没量到」读成「读取没超」。
2. **备份体积**：`memory/06-constraints.md` 技术债行记明 d1-backup.yml 因转 public 已 fail-closed、不再上传全库明文导出物 ⇒ 体积无登记无判据。
3. **业务体量三项**（[registry:bl-sku]、[registry:bl-orders-30d]、[registry:bl-peak-order-items]）：仅人工读数，无机器现值与自动触线。
4. **R2/对象存储体积**：无登记无判据。
5. **性能线网络类缺失**：customer 侧本机不可达时段缺失（NO_FCP + about:blank），不得折进基线，也不得反读成「顾客端很慢」。
6. **按类排除的记忆件**：`npm run verify:volume` 命中但排除的 02-structure.md、04-file-map.md、2026-09-26.md（sync 快照/append-only 日报）是「不判」不是「通过」；本轮机器读数另印外层面 38586B / shell_max 40960B（余 2374B），与单卷红线是两把尺，不得混用。

## 7. 撤销条件

- **整体撤销**：当且仅当 (a) 三类体量并入另一份权威文档且 [registry:*] 引用迁移完成，或 (b) `npm run verify:governance` 撤销且其「登记⇄现值」职责由新对账判据承接、`docs/governance/registry.json` 节点全部迁走。两者须附迁移后引用清单。
- **单指标撤销**：某指标连续 3 轮读数不构成任何判决（NO-LINE 无消费者），按「没有阈值消费者不算通过」降级为观察项移出本文，登记册标 deprecated；重新入册须附新消费者。
- **阈值撤销**：任何阈值只有在撤销条件写明（触发条件+证据形态）时才可删。凭「一直没触线」删阈值不受理——这正是「冻结增长就是红线」的反面。
- **记忆卷红线撤销**：仅当单卷硬上限被替换为更严登记、且 `npm run verify:volume` 对应腿就位时，[registry:rl-memory-volume] 旧档才失效；任何情况下不得用「外层面宽松」换取撤销单卷红线。
